# Security review and threat model

| Asset or boundary | Control | Residual risk |
| --- | --- | --- |
| Contract funds | Owner signs one-yocto approvals. The contract matches recipient, amount, expiry and invoice digest and checks the reservation. Transfer uses the stored terms. | A compromised or mistaken owner can approve incorrect terms. Compare the recipient against a trusted source before signing. An untrusted invoice may itself contain modified terms. |
| Agent key | Separate account. The backend checks a finite allowance and exact method and receiver before signing. The contract also checks predecessor. | A compromised backend can execute approved mandates, choose their timing, burn allowance or expose local invoices. An agent account full-access key bypasses the runtime access-key scope and still faces contract authorization. |
| Invoice content | SHA-256 from raw bytes, bounded input, validated output, warning patterns, and explicit operator verification. The model receives no signing tools. | Detection is partial. Attackers can change actual invoice fields or submit distinct documents for the same economic obligation. The contract digest deduplicates identical bytes. A normalized supplier and invoice-number match among the displayed documents warns the reviewer about possible economic duplicates. |
| Async payment | `PROCESSING` is written before scheduling the transfer. Settlement requires a private callback, a matching attempt and exactly one receipt. Only proven transfer failures permit retry. | A lost or failed callback can leave funds locked pending investigation. There is no administrative retry/reset method. |
| Duplicate or concurrent execution | Unique mandate ID, active/paid digest index, serialized receipt processing by NEAR, and a lock during transfer. | A single local service serializes agent requests. SQLite permits one unresolved broadcast per signer, including across contracts. Finalized but unsettled transfers hold their own mandate lock. A crash before broadcast can require investigation and block new requests for that signer. |
| Contract account | Deployment and initialization require the contract account. Owner and agent accounts are separate. | A contract full-access key can change code or drain funds. Restrict this key outside the app. The MVP has no upgrade or recovery governance. |
| Private data | API routes validate the loopback Host and the browser Origin. Cookie-authenticated requests also require the application request header. Direct navigations lack it, and the API grants no cross-origin access for it. The operator session uses a random HttpOnly, SameSite=Strict cookie with a four-hour limit and server-side revocation. Eight failed logins in one minute trigger throttling. Production HTML restricts script execution with a fresh CSP nonce. | The app is single-workspace. Local OS access, browser scripting compromise, backups or cloud inference can expose invoices. Treat account IDs and hashes on-chain as public. |
| RPC and explorer | Testnet-only RPC endpoint. Reconciliation checks transaction hash, signer and contract. A processing event and one successful terminal event must match the same attempt before settlement is recorded. | The configured RPC is trusted for chain views and receipt data. Outages affect availability. An explorer link can take time to resolve. |
| Dependencies | Pinned main dependencies, npm/Cargo locks and dependency scans listed in the verification report. | Wallet connectors may load vendor code at runtime. Wallets, RPC and Cloud require separate trust and operational review. |

The browser and AI have no owner signing key. The operator token is independent of the wallet and does not authorize contract funding, approval or cancellation. The workspace can send only contract-checked executions through the scoped agent key.

The project has not received an independent security audit. Use isolated Testnet accounts and test funds.
